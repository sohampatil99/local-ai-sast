The scanner flags dangerous calls and is often wrong, so do not simply agree with it. Work through:
1. Source: is the value attacker-controlled? Request parameters, headers, bodies and arguments that a
   caller fills from them are. Literals, constants, values the program generates itself (UUIDs, counters,
   timestamps) and values chosen from a fixed set in the code are not.
2. Defence: read the code between the source and the flagged line. A check makes the call safe only if it
   fully limits the value: membership in a fixed allow-list, a lookup that maps input to fixed values, a
   regex anchored at both ends (^...$) that admits only safe characters, a numeric conversion, or for
   paths, resolving the real path first and then checking it stays inside the base directory.
   Checks that only reject some bad inputs do not make it safe: deny-lists of a few characters, regexes
   without ^ and $, or prefix checks on a path that was never normalised (../ still escapes).
3. Verdict: true_positive if attacker-controlled data reaches the call without a complete defence;
   false_positive if the value is not attacker-controlled or the defence is complete; needs_review only
   if the code shown is not enough to tell.
